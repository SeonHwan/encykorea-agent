## 2026-10-08 · 0-4 · Qdrant 실행 방식

**결정**: `infra/compose.yaml`로 `qdrant/qdrant:v1.19.2`(CPU 이미지)를 실행한다.

| 항목 | 선택 | 근거 |
|---|---|---|
| 버전 | `v1.19.2` 태그로 고정 | 2026-10-05 릴리스, 시작 시점의 최신 안정 버전 (GitHub 릴리스 확인). `latest`·`v1.19`는 새 버전이 나오면 가리키는 이미지가 바뀐다 |
| 이미지 | CPU 이미지 (`-gpu-nvidia` 아님) | Qdrant GPU 인덱싱은 CUDA가 아니라 Vulkan을 쓴다. WSL에는 NVIDIA Vulkan 드라이버(`libGLX_nvidia`)가 없고, Qdrant 문서도 Windows 미지원으로 적혀 있다. 고려시대 청크 수만 개 규모는 CPU 인덱싱으로 충분하다고 예상 → Phase 2에서 인덱싱 시간을 재서 다시 판단 |

| 프로젝트 이름 | `name: encykorea` | 볼륨이 `infra_…`가 아니라 `encykorea_qdrant_storage`가 된다 |
| 재시작 | `restart: unless-stopped` | WSL 재접속 때 자동으로 켜지고, 직접 `stop`한 경우는 그대로 둔다 |

## 2026-10-08 · 0-5 · Python 버전

**결정**: 프로젝트 Python은 **3.13**. 로드맵 초안의 3.11에서 바꿨다. uv가 받은 Python을 쓰고, 시스템 Python(3.14.4)은 쓰지 않는다.

| 확인 | 결과 |
|---|---|
| PyTorch CUDA 빌드 | `download.pytorch.org/whl/cu130`의 torch 2.14.1이 cp310~cp315, `cu128`의 최신 2.11.0이 cp310~cp314 제공 → 3.13은 둘 다 가능 |
| 3.11 지원 기간 | PEP 664: 2027-10 보안 업데이트 종료. 프로젝트 도중에 끝날 수 있다 |
| 3.14 | 출시 1년 정도. 일부 패키지 지원이 늦을 수 있어 제외 |
| 3.13 | 출시 2년, 보안 지원 2029년까지 (출시 후 5년 규칙으로 계산. 수명표 사이트는 인증서 오류로 직접 확인 못 함) |

시스템 Python을 쓰지 않는 이유: Ubuntu 도구가 쓰는 Python이라 `pip install`이 막혀 있고(`externally-managed-environment`), OS 업그레이드 때 버전이 바뀐다.

**버전을 지키는 장치** (`/tmp` 복사본으로 확인, uv 0.12.23)

| `requires-python` | `.python-version` | `uv run python` 결과 |
|---|---|---|
| `>=3.13` | `3.13` | 3.13.16 (현재) |
| `>=3.13` | `3.14` | 3.14.4. 시스템 Python으로 조용히 바뀜 |
| `>=3.13` | 없음 | 3.14.4. 조용히 바뀜 |
| `>=3.14` | `3.13` | 오류로 멈춤 (`incompatible with the project's Python requirement`) |

→ `.python-version`을 반드시 커밋한다. `requires-python` 상한(`<3.14`)은 0-6에서 PyTorch lock 결과를 보고 정한다.

**결과**: uv 0.12.23 설치 (`UV_NO_MODIFY_PATH=1`, `~/.local/bin`은 이미 PATH에 있음). `uv init --bare` + `uv python pin 3.13`.
`uv run python --version` → `Python 3.13.16`, 실행 파일은 `.venv/bin/python` → `~/.local/share/uv/python/cpython-3.13-…`.

## 2026-10-08 · 0-6 · PyTorch CUDA 빌드

**결정**: `torch==2.14.1`을 `download.pytorch.org/whl/cu130`(CUDA 13.0)에서 받는다. `requires-python`은 `">=3.13,<3.14"`로 좁힌다.

| 확인 | 결과 |
|---|---|
| GPU | RTX 5060, compute capability **12.0**, VRAM 8GB, 드라이버 617.14 (CUDA 13.4까지) |
| 빌드별 12.0 포함 여부 (`v2.14.1` `.ci/manywheel/build_env_setup.py`) | `cu126` 미포함(최대 9.0). `cu130`·`cu132` 포함. `cu128`은 2.11.0이 마지막 |
| 기본 빌드 (`generate_binary_build_matrix.py`) | `CUDA_STABLE = "13.0"` |
| CUDA Toolkit 설치 | 필요 없음. CUDA 라이브러리가 `nvidia-*` 패키지로 같이 설치된다 (`.venv` 5.2GB) |

**`requires-python` 상한** (`/tmp` 복사본에서 `uv lock` 비교)

| 범위 | lock에 기록된 torch wheel | `uv.lock` 줄 수 |
|---|---|---|
| `>=3.13` | cp313·cp314·cp314t·cp315·cp315t × 3 플랫폼 = 15종 | 466 |
| `>=3.13,<3.14` | cp313 × 3 플랫폼 = 3종 | 376 |

**버전 고정**: `uv add "torch==2.14.1"`. 범위(`>=`)로 두면 `uv lock --upgrade` 때 같이 올라가서 임베딩 측정을 비교할 수 없다.

**결과**: `torch.cuda.is_available()` → `True`. `arch_list`에 `sm_120` 포함.
4096×4096 float32 행렬곱: GPU 11.3ms, CPU 227ms (약 20배). GPU·CPU 결과 최대 차이 0.0011 (float32 합산 순서 차이 수준).

## 2026-10-08 · 1-4 · 수집 범위 변경: API 목록 전체

**결정**: 고려 항목만 고르지 않고 **API 목록 전체 15,836건**의 본문을 받는다.

| 항목 | 고려 범위 (이전) | 목록 전체 (현재) |
|---|---|---|
| 항목 수 | 1,614건 | 15,836건 |
| 예상 수집 시간 (요청 약 0.2초 + 간격 1초) | 약 35분 | 약 5시간 20분 |
| 예상 크기 (「가경전」 8KB 기준) | 약 13MB | 약 130MB |

**이렇게 정할 수 있는 이유**
- 본문을 받을 수 있는 건 어차피 목록 15,836건뿐이다 (1-3). 시대로 다시 걸러 낼 이유가 적다.
- 고려 범위 밖 질문(조선·근현대 등)에도 답할 근거가 생긴다. 1-3에서 "모른다" 처리용으로 생각한 범위 밖 질문은 API 목록 밖 항목(「강감찬」·「노비안검법」 등)으로 남는다.

**목록 밖 eid 표본 확인** (eid를 직접 넣어 보는 방식으로 확인)

| 확인 | 결과 |
|---|---|
| CSV(`encykorea_20240130.csv`) eid | 73,587개, `E0000002`~`E0080590`. 그중 API 목록 밖 **60,166개** |
| 목록 밖 60,166개 중 무작위 30개 (시드 `20261008`, 1초 간격) | **30개 모두 HTTP 204, 0바이트** (200은 0개) |
| 1-3의 확인과 합치면 | 목록 밖 eid 42개 중 42개가 204 |
| 3의 법칙 (n개 중 0개 발견 → 비율 95% 상한 3/n) | 목록 밖에서 본문이 나오는 비율은 7% 미만까지만 말할 수 있다 |
| `E0000001`부터 1씩 올리면 | 약 81,600번, 1초 간격으로 약 27시간 |

→ 먼저 목록 15,836건을 받는다. 목록 수집이 끝난 뒤 CSV에만 있는 60,166개를 밤새 돌려 204인지 전수 확인할 수 있다
(수집 코드가 eid 목록만 받아 처리하고 204는 건너뛰므로 그대로 쓸 수 있다). 편찬실 답변이 오면 그에 따라 정한다.

**주의**
- 수집이 5시간 넘게 걸린다. 끊겨도 이어받을 수 있어야 한다 (이미 받은 파일은 건너뛴다).
- 호출 한도는 아직 모른다 (편찬실 답변 대기). 429가 나오면 간격을 늘린다.

인덱스(keyword)는 이름·종류가 같아서 그대로 둔다. 벡터는 바뀌지 않으므로 인코딩을 다시 하지 않고 payload만 덮어쓴다 (`set_payload`).

**동의어 처리는 질문 해석 단계로 미룬다**: "조선 말기"와 "조선 후기"처럼 같은 뜻의 다른 표현은 `search.py`에서 표로 처리하지 않는다.

허용 값은 코드에 적지 않고 Qdrant의 `facet`으로 읽는다 (데이터가 바뀌어도 어긋나지 않게).

## 2026-10-14 · 3-4 · sparse·hybrid(RRF) 측정 (`src/phase3/eval_retrieval.py`)

**방식**: 3-3과 같은 질문 30개·같은 판정으로 dense / sparse / hybrid를 비교한다. 각 방식은 상위 50개를 받고, hybrid는 dense 50개와 sparse 50개를 RRF로 합친 뒤 상위 50개를 쓴다.

| 지표 | dense 항목 | sparse 항목 | hybrid 항목 | dense 섹션 | sparse 섹션 | hybrid 섹션 |
|---|---|---|---|---|---|---|
| recall@1 | 0.567 | 0.600 | 0.633 | 0.533 | 0.533 | 0.567 |
| recall@5 | 0.800 | 0.833 | 0.900 | 0.733 | 0.833 | 0.867 |
| recall@10 | 0.933 | 0.900 | 0.967 | 0.867 | 0.900 | 0.933 |
| recall@50 | 1.000 | 0.967 | 0.967 | 0.967 | 0.967 | 0.967 |
| MRR | 0.655 | 0.695 | 0.749 | 0.617 | 0.645 | 0.691 |

**관찰**
- hybrid가 recall@1·5·10과 MRR에서 dense와 sparse보다 높다. 다만 차이가 질문 두세 개 수준이다 (recall@1 항목 기준 dense 17개 → hybrid 19개). 30개로는 우연일 수 있어 "hybrid가 낫다"고 결론내지 않는다.
- 두 방식은 맞히는 질문이 다르다. sparse가 나은 질문: q01(7→1)·q24(10→1)·q20·q22(3→1). 질문의 낱말이 본문이나 접두사에 그대로 있는 경우.
  dense가 나은 질문: q03(7→36)·q05(46→없음)·q16(1→8). 질문이 본문과 다른 말로 풀어 쓴 경우. hybrid는 이 중 q24·q20·q22·q16·q12·q26을 건졌지만 q01(1→3)·q03(7→9)은 한쪽보다 나빠졌다.
- recall@50은 hybrid(0.967)가 dense(1.000)보다 낮다. q05는 dense 46위였는데 hybrid 후보 안에서 50위 밖으로 밀렸다. 후보 수(50개씩)를 늘리면 달라질 수 있으나 확인하지 않았다.
- q05(세 방식 모두 약함)·q21(3위에서 정체)은 3-5에서 열어 볼 후보. q07은 hybrid에서 항목 2위인데 정답 섹션은 31위.

**서버 RRF를 쓰지 않고 직접 합친 이유 (재현성)**
- 처음에는 Qdrant 서버의 RRF(`query_points`의 `prefetch` + `RrfQuery`)로 합쳤다. 같은 코드를 두 번 돌리자 q07의 hybrid 섹션 순위가 31 → 32로 달랐다.
- 원인은 **점수가 같은 청크의 순서를 서버가 매번 같게 정하지 않는 것**이다 (같은 질문을 4번 받으면 동점 청크의 앞뒤가 바뀜). RRF는 순위만 쓰기 때문에 동점이 잦다 (dense 1위+sparse 5위 = dense 5위+sparse 1위).
- 그래서 `rrf_fuse`로 파이썬에서 직접 합친다. 점수가 같으면 `chunk_id` 오름차순으로 놓는다. 3회 돌려 질문별 순위 30줄이 모두 같았다.
- 3-3의 "3회 동일"은 dense만의 결과였다 (dense 점수는 거의 겹치지 않아 동점이 드물다).
- `search_hybrid`(서버 방식)는 대조용으로 코드에 남겼다.

**서버 RRF와 직접 구현의 대조**
- 점수 공식: 서버는 `1 / (k + 순위)`에서 **순위를 0부터** 센다 (1위가 `1/60`). 처음 "1위면 1/61"이라고 설명한 것은 틀렸다. 서버 점수와 0부터 센 계산이 청크 8개에서 4자리까지 일치했다.
- 30개 질문에서 같은 청크의 점수 차이는 최대 2.6e-09. 공식은 같다.
- 50위 경계에서 서버와 직접 구현이 고르는 청크가 다를 수 있다 (50위와 51위의 점수가 같을 때. q08에서 확인). 직접 구현은 `chunk_id` 순으로 항상 같게 고른다.
- `k=60`은 원 논문의 관례값이며 `Rrf(k=60)`으로 명시했다. Qdrant의 `Fusion.RRF` 기본 `k`는 확인하지 못했다. `Prefetch.limit` 기본값이 10이라 후보 수(50)를 명시해야 한다.

**코드 변경**: `evaluate(client, model, queries, mode)`가 `mode`(dense / sparse / hybrid)를 받는다. `main`이 세 방식을 나란히 출력한다.

## 2026-10-14 · 3-6 · 리랭커 실험: bge-m3 colbert MaxSim (`src/phase3/eval_retrieval.py`)

## 2026-10-14 · 3-7 · Contextual Retrieval 실험 (`src/phase3/contextualize.py`, `context_collections.py`)

**결정**: 문맥 주입은 채택하지 않는다. 전체 청크 75,122개에 적용하는 작업은 비용 때문에 하지 않는다.
작은 실험(청크 2,733개)에서 문맥 없음 대비 개선이 없었고 대부분 지표가 약간 내려갔다.

**방식**: `claude-sonnet-5-5`가 항목 전체 글과 청크 하나를 보고 "항목 이름과 조각의 주제를 짚는 80자 이내 한 문장"을 쓴다 (`make_context`). 이 문장을 `embedding_text` 맨 앞에 붙여 다시 인코딩했다.
처리 범위는 평가 질문 30개의 정답 항목 27개 + 무작위 500개 항목 (seed 42) = 항목 527개, 청크 2,733개.
같은 청크로 컬렉션 두 개를 만들어 비교했다: `ctx_off`(기존 `embedding_text`), `ctx_on`(문맥 + 기존 `embedding_text`). 임베딩·검색 방식은 같고 포인트 id도 같다.
`ctx_off`의 벡터가 기존 컬렉션의 같은 청크와 코사인 1.0000으로 같아 조건이 재현됨을 확인했다. 기존 컬렉션 `encykorea_chunks`(75,122개)는 건드리지 않았다.

| 항목 기준 | dense off → on | sparse off → on | hybrid off → on |
|---|---|---|---|
| recall@1 | 0.933 → 0.900 | 0.900 → 0.867 | 0.933 → 0.900 |
| recall@5 | 1.000 → 0.967 | 0.967 → 0.933 | 1.000 → 1.000 |
| MRR | 0.951 → 0.924 | 0.928 → 0.901 | 0.961 → 0.942 |

**질문별**: 대부분 변화 없음(1위 → 1위).
- 나빠진 질문: q03(백성이 군대 대신 내던 베의 부담을 줄이고, 부족해진 나라 재정을 다른 세금으로 메운 영조 때의 개혁은 무엇입니까?) dense 1→4·sparse 2→7·hybrid 1→4, q05(신석기시대 사람들이 곡식이나 물을 담아 쓰던, 겉면에 선을 새긴 대표적인 그릇은 무엇입니까?) dense 5→8·sparse 13→16.
- 좋아진 질문: q29(통일신라 때 당나라에 유학한 학자이자 문장가는 누구입니까?) hybrid 3→2, q14(의상이 당나라 종남산 지상사에서 배운 스승은 누구입니까?) sparse 섹션 2→1, q07(고구려가 멸망한 뒤 만주 지역에서 고구려 유민과 말갈족이 세운 나라는 어떻게 성립하고 발전했습니까?) hybrid 섹션 4→2.
- q03을 열어 보니 균역법 청크의 점수가 모두 내려갔고(`의의와 평가` 0.5373 → 0.4971, `제정 목적` 0.5150 → 0.4851) 경쟁하는 「양역」 청크는 거의 변하지 않아 순위가 뒤집혔다.
  균역법 청크 12개의 문맥 문장이 모두 "균역법 항목의 ○○ 부분으로 …를 다룬다" 꼴이고 질문의 말(군포·베·감필)과 겹치지 않았다.
  같은 틀의 문장이 청크끼리 서로 닮게 만들었을 가능성은 가설이고 청크 간 유사도는 재지 않았다.

**한계 (결론을 읽을 때 반드시 감안)**
- 후보 풀이 2,733개로 작아서 `ctx_off`도 recall@5가 1.000에 가깝다. 천장에 가까워 개선 여지가 작게 측정된다. 절대 수치를 3-4(전체 75,122개)와 비교하면 안 된다. "문맥이 효과 없음"과 "측정이 포화됨"을 이 실험은 구분하지 못한다.
- 질문 30개로는 recall@1 0.933 → 0.900(질문 1개)을 우연과 구분할 수 없다. "개선이 확인되지 않음"이지 "악화가 확인됨"이 아니다.
- 시험한 변형이 하나뿐이다: 문맥을 `embedding_text` 맨 앞에, 80자 한 문장, 한 가지 지시문, 한 모델. 위치·길이·형식을 바꾸면 결과가 달라질 수 있다.
- 문맥 문장의 사실 정확성은 표본 몇 개만 눈으로 봤다. 본문과 일일이 대조하지 않았다.

**한계 (이 결정을 읽을 때 감안)**
- 질문 30개이고 제가 직접 골랐다. 본문 첫 문장과 가까운 쉬운 질문이 많아서 절대 수치가 높게 나왔을 수 있다 (3-1). 유형별 8개 안팎이라 유형별 비교는 더 불안정하다.

## 2026-10-14 · 4-7 · 출처 표기 (`src/phase4/answer.py`)

**결정**: 출처 줄은 모델이 쓰지 않고 **코드가 붙인다**. 최종 답변에서는 본문의 근거 번호 `[n]`을 지운다 검색 안내 문구("백과사전에서 '용어'로 검색")는 넣지 않는다.

**흐름** (`attach_sources`): 모델이 문장 끝에 붙인 `[n]`을 읽는다(`cited_numbers`) → 번호를 항목명으로 바꿔 출처 줄을 만든다(`build_source_line`) → 본문에서 번호를 지운다(`strip_numbers`). 번호를 지우기 전에 읽는 순서가 중요하다.
최종 모양: `본문` + 빈 줄 + `출처: 「항목명」, 「항목명」, ⓒ한국민족문화대백과사전`.
- 같은 항목이 여러 번호에 걸리면 한 번만 쓴다 (인용한 순서 유지). 범위 밖 번호는 무시한다.
- 인용이 없는 답("제공된 근거로는 답할 수 없습니다")에는 출처 줄을 붙이지 않는다.
- 번호를 지울 때 앞 공백, 줄 끝 공백, 이중 공백을 함께 정리하고 문단 구분(빈 줄)은 유지한다.
- `answer_question`(검색 → 근거 글 → 모델 호출 → 출처 붙이기)과 `prepare_input`(모델을 부르기 전까지)을 추가했다. `prepare_input`의 결과가 4-6 저장본의 근거 글·`sources`와 완전히 같음을 확인했다.

**확인**
- `cited_numbers`: 4-6에서 저장한 답변 14개에서 번호가 문장 끝·마침표 뒤·줄 끝 어디에 있어도 읽었다 (범위 밖 번호 0개). 위치를 보지 않고 `[숫자]`만 찾아서, 4-6의 낱말 점검이 번호 위치 때문에 실패한 문제가 없다.

**한계**

## 2026-10-14 · 4-9 · 프롬프트 캐싱: 지금 구조에서는 적용되지 않음 (코드 변경 없음)

**결정**: 답변 생성(`answer_question`)에 프롬프트 캐싱을 넣지 않는다. 시스템 프롬프트가 캐시 최소 길이에 못 미쳐 적용되지 않았고, 근거 글은 질문마다 달라 캐시 대상이 아니다. Phase 5(에이전트)에서 다시 본다.

**확인한 것** (확인용 스크립트로 호출 3번, `count_tokens`는 비용 없음)
- 시스템 프롬프트는 260자. `count_tokens`로 시스템 프롬프트 + 짧은 질문이 238토큰.

**확인하지 못한 것**
- 이 모델의 정확한 캐시 최소 길이. 문서에는 모델별로 512~4096토큰이라고 되어 있다고 알고 있으나 이 세션에서 값을 확인하지 않았다. 238~292토큰에서 안 된 것과 약 8,700토큰에서 된 것만 안다.

**왜 이 구조에서는 이득이 없는가**
- 캐시는 요청의 **앞부분이 글자 하나까지 같아야** 적용된다 (prefix 일치). 이 프로젝트의 질의응답에서 질문마다 같은 것은 시스템 프롬프트(약 240토큰)뿐이고, 그 뒤의 근거 글은 질문마다 다르다.
- 캐시 서버는 Anthropic 쪽에 있다. 호출하는 쪽은 캐시할 블록에 `cache_control`을 붙일 뿐이다. 적용되지 않아도 오류가 나지 않아서 `usage`의 `cache_read_input_tokens`로만 확인할 수 있다.
- 캐시를 위해 시스템 프롬프트를 길게 늘리는 것은 하지 않는다 (프롬프트의 목적이 아니라 캐시 때문에 늘리는 것).

**Phase 5에서 다시 볼 것**: 에이전트가 한 대화 안에서 여러 번 호출하면 도구 정의와 대화 이력이 요청의 앞부분으로 반복되어 캐시가 이득일 수 있다. 그때 `cache_read_input_tokens`로 확인한다.

**이 결정이 말해 주지 않는 것**

- **사전 내 충돌**: 에이전트가 인용한 근거 하나에는 충실해도, 사전의 다른 항목과 어긋나는 서술을 그대로 옮겼다. 같은 사건(의종의 죽음)을 n15에서는 이의방이, h02에서는 이의민이 시해했다고 서술했다. 사전 안에 어긋남이 있고(`김보당의 난`은 이의방, `의종`·`희릉`은 이의민) 모델이 알아채지 못한 사례다. 이 열은 우연히 발견한 것이라 체계적으로 찾지 않았고, "없음"이 곧 충돌이 없다는 뜻이 아니다.
