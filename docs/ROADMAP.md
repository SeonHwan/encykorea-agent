# 한국사 백과사전 에이전트 — 학습 로드맵

> 「한국민족문화대백과사전」을 지식원으로, 한국 역사·문화 질문에 근거를 달아 답하는 AI 에이전트를
> 처음부터 만든다. 각 Phase는 **작은 단계로 나눠 진행**하고, 단계마다 코드를 이해한 뒤 다음으로 간다.

---

## 0. 프로젝트 개요

### 만들 것

```
사용자: "태조 왕건은 언제 태어났고, 주요 업적은 뭐야?"
에이전트:
  1. 질문 분석 — 사실(출생 연도) + 서술(업적)이 섞인 질문
  2. 사실 조회 도구 → 왕건 출생 877년
  3. 백과사전 검색 도구 → 「왕건」 항목의 업적 문단
  4. 답변 + 출처
     "왕건은 877년에 태어났습니다. … 936년 후삼국을 통일했습니다.
      출처: 「왕건」, ⓒ한국민족문화대백과사전"
```

### 두 갈래 구조

| 질문 유형 | 예시 | 처리 방식 |
|---|---|---|
| **서술형** | "왕건의 업적은?", "훈민정음은 왜 만들었나?" | **RAG**: 청킹 → 임베딩 → 벡터 검색 → 답변 생성 |
| **사실형** | "왕건은 언제 태어났나?", "고려는 몇 년에 세워졌나?" | **정형 조회**: 인물·사건 데이터를 표로 뽑아 두고 도구로 조회 |
| **복합·시간 축** | "후삼국 통일 과정을 순서대로", "세종 재위 중 주요 사건" | **에이전트**: 두 도구를 여러 번 호출하고 연도순으로 정리 |

### 데이터

| 항목 | 내용 |
|---|---|
| 출처 | 한국학중앙연구원 「한국민족문화대백과사전」 (encykorea.aks.ac.kr) |
| 규모 | 항목 7만여 개 (공공데이터포털 목록 73,587건). **OpenAPI로 본문을 받을 수 있는 건 목록의 15,836건뿐** (1-3에서 확인, `docs/decisions.md`) |
| 라이선스 | 항목 본문은 **공공누리 제1유형**: 출처 표기 조건으로 자유 이용 |
| 출처 표기 | `출처: 「항목명」, ⓒ한국민족문화대백과사전` (+ 항목 URL) |
| 데이터 범위 | **수집된 15,836건 전체** (1-4에서 고려 1,614건에서 넓힘, `docs/decisions.md`) |

미디어(사진 등)는 공공누리 마크가 붙은 것만 쓸 수 있다. 이 프로젝트는 **텍스트만** 다룬다.

### 전체 아키텍처

```
[Phase 1] raw/*.json (수집 완료) ──▶ 정제·섹션 분할 ──▶ chunks.jsonl
[Phase 2]                              chunks.jsonl ──▶ bge-m3 (dense + sparse) ──▶ Qdrant
[Phase 3]                 평가 질문 ──▶ 검색 품질 측정 ──▶ hybrid·리랭커·문맥 보강 실험
[Phase 4]                              raw/*.json ──▶ 사실 추출 ──▶ SQLite (인물·사건·연도)
                          검색 결과 + 사실 ──▶ Claude ──▶ 출처 달린 답변
[Phase 5]                 사용자 질문 ──▶ 에이전트 (도구: 검색 / 사실 조회 / 연표) ──▶ 답변
```

## Phase 0. 개발 환경

**목표**: WSL 안에서 Python·Docker·Qdrant·GPU가 모두 동작하는 상태.

**배울 개념**: WSL2, Docker Engine과 컨테이너, 포트 바인딩, Docker 볼륨, CUDA

| 단계 | 할 일 | 확인 |
|---|---|---|
| 0-1 | WSL2 + Ubuntu 설치 | `wsl -l -v`에 Ubuntu가 VERSION 2로 보임 |
| 0-2 | Ubuntu 기본 설정 (사용자, apt 업데이트, git 신원) | `git config --global user.email` |
| 0-3 | Docker Engine 설치 (WSL 안에 직접) | `docker run hello-world` |
| 0-4 | Qdrant를 `infra/compose.yaml`로 실행 | `curl localhost:6333/healthz` |
| 0-5 | uv + Python 3.13 프로젝트 생성 | `uv run python --version` |
| 0-6 | GPU 확인 (NVIDIA 드라이버 → WSL CUDA → PyTorch) | `torch.cuda.is_available()` → True |
| 0-7 | 레포 생성 + 첫 커밋 | `git log` |

**설계 원칙**
- Qdrant 포트는 `127.0.0.1:6333`에만 연다. 인증 없는 로컬 서버가 다른 기기에 노출되지 않게.
- Qdrant 이미지는 버전을 고정한다 (`latest` 금지). 받는 날마다 서버가 달라지면 측정을 비교할 수 없다.
- 데이터는 이름 붙은 Docker 볼륨에 둔다. 컨테이너를 지워도 컬렉션이 남는다.
- RTX 50 시리즈는 최신 CUDA(12.8 이상)를 지원하는 PyTorch 빌드가 필요하다.
- Docker Desktop은 대기업에서 유료 구독 대상이다. WSL 안에 Docker Engine을 직접 설치한다.

**완료 기준**: Qdrant 대시보드(`http://localhost:6333/dashboard`)가 열리고, Python에서 GPU가 보인다.

## Phase 1. 데이터 정제와 청킹

**목표**: 수집된 항목(15,836건) 본문을 검색 단위(청크)로 잘라 `chunks.jsonl`을 만든다. 수집은 끝났고 원본은 `data/raw/{eid}.json`에 있다고 가정한다.

**배울 개념**: 원본 보존(raw) 원칙, 토큰과 토크나이저, 청크 크기·오버랩, 메타데이터 설계, JSON과 JSONL

### 1-A. 수집 (완료)

| 단계 | 내용 |
|---|---|
| 1-1 ~ 1-3 | 이용 조건 확인, 응답 구조 정리, 수집 범위 결정 (`docs/decisions.md`) |
| 1-4 | 항목별 본문 수집. **완료**: 15,836개, `data/raw/{eid}.json` 개수 = 목록 수 |
| 1-5 | ~~`manifest.json`~~ 생략. 수집 일시·개수·실패 0건은 `decisions.md` "1-4 · 수집 결과"에 기록 |

**설계 원칙**
- 원본 응답은 **가공하지 않고 그대로** 저장한다. 파서를 고쳐도 원본을 다시 받지 않는다.

### 1-B. 정제와 청킹

| 단계 | 할 일 | 확인 |
|---|---|---|
| 1-6 | 본문 구조 파악 (정의·요약·본문의 소제목, 각주, 표). **완료**: 전체 15,836건 집계 + 청킹 방식·크기·필드별 처리 결정 (`decisions.md` "1-6") | 소제목·문단·토큰 분포, 청크 수 시뮬레이션 |
| 1-7 | `parse.py`: 항목 → 섹션(소제목 경로 + 문단). **완료**: `data/sections.jsonl` 15,836줄 (git 제외, `uv run python src/phase1/parse.py`로 다시 만든다) | `sections.jsonl` |
| 1-8 | `chunk.py`: 섹션 → 청크 (bge-m3 토크나이저로 토큰 수 측정). **완료**: `data/chunks.jsonl` 75,122개 (git 제외, `uv run python src/phase1/chunk.py`로 다시 만든다) | 청크 수, 평균·최대 토큰 |
| 1-9 | 청크 품질 점검: 너무 짧은 청크, 너무 긴 청크, 잘린 문장 | 20토큰 미만 비율 |
| 1-10 | 뷰어로 원문과 청크를 나란히 확인 | 항목 몇 개 직접 읽기 |

**청크 한 개의 모양 (예정)**
```json
{"eid": "E00xxxxx", "title": "왕건", "field": "역사/고려시대", "era": "고려",
 "path": ["왕건", "생애 및 활동사항"], "chunk_index": 2, "n_chunks": 7, "n_tokens": 418,
 "text": "918년 궁예를 몰아내고 즉위하여 국호를 고려라 하였다. …",
 "embedding_text": "[왕건 > 생애 및 활동사항]\n918년 궁예를 몰아내고 …",
 "url": "https://encykorea.aks.ac.kr/Article/E00xxxxx"}
```
필드 이름·`eid` 형식·분야 표기는 예시다. 1-2에서 실제 API 응답을 보고 확정한다.

**설계 원칙**
- 청크는 512토큰 안팎, 문단 경계를 지키며 묶는다. 앞 청크의 짧은 마지막 문단은 다음 청크에 겹쳐 넣는다.
- `text`(LLM이 읽는 원문)와 `embedding_text`(검색용, 항목명·소제목 접두사)를 분리한다.
- 20토큰 미만 청크는 이웃에 합친다. 내용 없는 짧은 청크는 엉뚱한 질문의 검색 상위에 올라온다.
- 토큰 수는 임베딩 모델과 **같은 토크나이저**로 잰다.

**완료 기준**: 수집한 항목 전체가 청크로 만들어지고, 청크 몇 개를 원문과 대조해 내용 손실이 없다.

## Phase 2. 임베딩과 벡터 DB 적재

**목표**: 청크를 벡터로 바꿔 Qdrant에 넣고, 질문으로 검색되는 것을 확인한다.

**배울 개념**: 임베딩, dense 벡터(1024차원)와 sparse 벡터(토큰 가중치), 코사인 유사도,
named vector, payload와 payload 인덱스, upsert, 임베딩 캐시, HNSW

| 단계 | 할 일 | 확인 |
|---|---|---|
| 2-1 | bge-m3로 문장 2~3개 인코딩해 보기 (GPU). **완료**: `src/phase2/encode_test.py`, dense 1024개·sparse 토큰 가중치 확인 | dense 1024개, sparse 토큰 가중치 출력 |
| 2-2 | 유사도 손계산: "왕건" vs "고려 태조" vs "세종". **완료**: `src/phase2/similarity_test.py`, 기대와 달리 왕건↔태조가 가장 낮음(단어 비교라 의미 작음, `decisions.md` 2-2) | 비슷한 쌍의 점수가 높음 |
| 2-3 | 컬렉션 설계: named vector `dense`/`sparse`, payload 인덱스 (`era`, `field`, `eid`). **완료**: `src/phase2/collection.py`, 컬렉션 `encykorea_chunks`, 인덱스 6개 (`decisions.md` 2-3) | 대시보드에서 스키마 확인 |
| 2-4 | `index.py`: 인코딩 → upsert (캐시는 두지 않기로 함, `decisions.md` 2-4). **완료**: `src/phase2/index.py`, 포인트 75,122개 적재 | 포인트 수 = 청크 수 |
| 2-5 | `search.py`: dense만 / sparse만 / 필터 검색. **완료**: `src/phase2/search.py`, 질문 5개 비교 (`decisions.md` 2-5). 질문 3은 데이터에 항목이 없어 약함 | 질문 5개로 결과를 눈으로 확인 |

**설계 원칙**
- 임베딩 캐시 키는 `sha256(임베딩할 텍스트)`이고, 파일명에 모델 이름을 넣는다. 바뀐 청크만 다시 인코딩한다.
- point id는 `uuid5(eid + 청크 순번)`처럼 결정론적으로 만든다. 다시 실행해도 같은 청크는 같은 id다.
- 항목 단위로 **기존 포인트를 지우고 다시 넣는다.** upsert만 하면 청크 수가 줄었을 때 옛 포인트가 남는다.
- sparse 벡터에는 IDF 보정을 붙이지 않는다. bge-m3의 sparse 가중치는 이미 학습된 값이다.
- 실험할 때는 새 컬렉션 이름으로 적재한다. 기준 컬렉션을 덮어쓰지 않는다.

**완료 기준**: "고려를 세운 사람은?" 같은 질문에 「왕건」 관련 청크가 상위에 나온다.

## Phase 3. 검색 품질 측정과 개선

**목표**: 검색 품질을 숫자로 재고, 실험으로 검색 방식을 고른다.

**배울 개념**: 평가셋과 정답 라벨, recall@k, MRR, 하이브리드 검색, RRF, 리랭커(colbert MaxSim),
Contextual Retrieval, 결정적(재현 가능한) 측정

| 단계 | 할 일 | 확인 |
|---|---|---|
| 3-1 | 평가 질문 30개 작성 (서술형·사실형·별칭형·시대형 섞기). **완료**: `src/phase3/eval_queries.json` (서술형 8·사실형 8·별칭형 6·시대형 8, `decisions.md` 3-1) | `eval_queries.json` |
| 3-2 | 정답 라벨: 질문마다 정답 항목(`eid`)과 소제목 경로. **완료**: `answer_sections` 30개 (섹션 `kind`·`path`, `decisions.md` 3-2) | 라벨이 너무 느슨하지 않은지 점검 |
| 3-3 | `eval_retrieval.py`: recall@1/5/10/50, MRR, 질문별 순위. **완료**: 항목 기준 recall@1 0.567·MRR 0.655, 섹션 기준 0.533·0.617 (`decisions.md` 3-3) | dense 기준선 |
| 3-4 | sparse, hybrid(RRF) 측정. **완료**: hybrid 항목 기준 recall@1 0.633·MRR 0.749 (dense 0.567·0.655). 서버 RRF는 동점 순서가 실행마다 달라 `rrf_fuse`로 직접 합침 (`decisions.md` 3-4) | 모드별 비교표 |
| 3-5 | 실패 질문을 하나씩 열어 보기 (`--dump`). **완료**: 8개를 열어 분류 (어휘 차이가 대부분, 청킹 단독 원인 없음). q03 라벨 1건 정정 (`decisions.md` 3-5) | 원인 분류: 어휘 차이 / 청킹 / 라벨 |
| 3-6 | 리랭커 실험. **완료(채택 안 함)**: bge-m3 colbert MaxSim으로 hybrid 상위 50개를 재정렬했더니 개선 1(섹션 기준 3)·악화 6, MRR 0.749→0.681. LLM 리랭킹은 Phase 4에서 비교 (`decisions.md` 3-6) | 개선·악화 질문 수 |
| 3-7 | Contextual Retrieval 실험 (청크마다 LLM이 문맥 한 줄을 써서 `embedding_text`에 붙임). **완료(채택 안 함)**: 청크 2,733개로 문맥 있음/없음 비교, 개선 없음. 전체 적용은 하지 않음 (`decisions.md` 3-7) | 비용과 개선 폭 |
| 3-8 | 기본 검색 경로 결정 + 근거 기록. **완료**: hybrid(dense 50 + sparse 50, `rrf_fuse`)를 기본으로 정함. 질문 30개의 한계를 함께 기록 (`decisions.md` 3-8) | `docs/decisions.md` |

**평가 질문 예시** (정답 항목명은 예시. 3-2에서 실제 항목을 확인해 확정)

| 유형 | 질문 | 정답 |
|---|---|---|
| 서술형 | 왕건이 호족을 포섭한 방법은? | 「왕건」 > 정책 관련 문단 |
| 사실형 | 고려가 후삼국을 통일한 해는? | 「후삼국 통일」 등 |
| 별칭형 | 고려 태조의 출신지는? | 「왕건」 (질문에 "왕건"이 없음) |
| 시대형 | 고려 광종의 개혁 정책 | 「광종」, 「노비안검법」, 「과거제」 |

**설계 원칙**
- 정답 라벨은 **구체적으로** 정한다. "이 단어가 들어 있으면 정답" 같은 느슨한 라벨은 엉뚱한 청크도 정답으로 센다.
  후보 중 라벨을 통과하는 비율을 같이 재서 라벨의 느슨함을 감시한다.
- RRF는 순위만 보고 합친다 (`1/(k + 순위)`). 동점 처리 규칙을 코드로 고정해 같은 측정을 두 번 하면 같은 결과가 나오게 한다.
- 모드끼리 점수를 직접 비교하지 않는다 (코사인 / sparse 내적 / RRF 점수는 단위가 다르다). 순위로 비교한다.
- 질문 수가 적으면 한 질문이 지표를 크게 움직인다. 지표와 함께 질문별 순위 변화를 본다.

**완료 기준**: 기본 검색 경로가 측정 근거와 함께 정해지고, 실패 질문의 원인이 분류되어 있다.

## Phase 4. 사실 데이터와 답변 생성

**목표**: (A) 인물·사건의 연도를 정형 데이터로 뽑고, (B) 검색 결과로 출처 달린 답변을 만든다.

**배울 개념**: 정보 추출(규칙 기반 / LLM 기반), 정형 스키마 설계, Claude Messages API, 시스템 프롬프트,
근거 기반 답변(grounding)과 인용(citations), 프롬프트 캐싱, 환각 방지

### 4-A. 사실 데이터 (**보류**: 4-B를 먼저 하고 4-A는 필요가 확인되면 한다, 2026-10-14)

> 보류 이유: 단일 사실 질문은 이미 검색으로 잘 찾고(Phase 3 사실형 8개 모두 dense 1위), 4-A가 필요한 질문 유형(범위·집계, 연표)은 평가 질문에 없다.
> 필요가 추론에 머물러 있어서 4-B에서 연도 오류나 범위 질문의 한계가 실제로 보이면 그때 다시 판단한다 (`decisions.md` 4-0).
> 5-1의 `lookup_person`·`list_events` 도구는 이 데이터를 전제하므로, 4-A를 하지 않으면 Phase 5에서 도구 구성을 다시 정해야 한다.

| 단계 | 할 일 | 확인 |
|---|---|---|
| 4-1 | 본문에서 사실 패턴 찾기 (생몰년, 재위 기간, 사건 연도, 별칭) | 항목 10개 수작업 정리 |
| 4-2 | 스키마: `person(eid, name, aliases, born, died, reign_start, reign_end)`, `event(eid, name, year, era)` | SQLite 테이블 |
| 4-3 | 추출기: 규칙(정규식) → 부족한 곳만 LLM 추출 | 추출 성공률 |
| 4-4 | 검증: 사실 질문 15개의 정답을 원문에서 직접 확인해 대조 | 정답률 |
| 4-5 | 조회 함수: `find_person(name)`, `events_between(start, end)` | CLI로 조회 |

### 4-B. 답변 생성

| 단계 | 할 일 | 확인 |
|---|---|---|
| 4-6 | 단일 호출: 질문 + 검색 청크 top-5 → Claude. **완료(관찰만)**: 8개 질문에서 Claude(`claude-sonnet-5-5`)와 GPT(`gpt-5.6-terra`)를 같은 근거·프롬프트로 비교. 모델은 아직 정하지 않음 (`decisions.md` 4-6) | 답변이 청크 안의 내용으로만 구성됨 |
| 4-7 | 출처 표기: 항목명을 답변에 붙임 (Citations 기능 사용). 본문 속 항목 링크·`eid`는 출력하지 않고 "백과사전에서 '용어'로 검색"으로 안내 (`decisions.md` 1-8). **완료(방식 변경)**: Citations 기능 대신 코드가 인용 번호를 읽어 출처 줄을 붙이고 본문 번호는 지움, 검색 안내 문구는 넣지 않음 (`decisions.md` 4-7) | 문장마다 근거 청크, 답변에 링크 없음 |
| 4-8 | "모른다" 처리: 근거가 없으면 지어내지 않고 모른다고 답함. **완료**: 질문 5개에서 두 모델 모두 근거 없을 때 지어내지 않음. "답할 수 없다"는 답에는 출처 줄을 붙이지 않음 (`decisions.md` 4-8) | 범위 밖 질문 5개 |
| 4-9 | 프롬프트 캐싱: 고정 시스템 프롬프트 캐시. **완료(적용 안 함)**: 시스템 프롬프트(약 240토큰)가 캐시 최소 길이에 못 미쳐 캐시 읽기 0, 근거 글은 질문마다 달라 대상이 아님. Phase 5에서 다시 봄 (`decisions.md` 4-9) | `cache_read_input_tokens` > 0 |
| 4-10 | **로컬 모델 비교**: 4-6 단일 호출을 로컬 대화 모델(RTX 5060 8GB에 들어가는 공개 모델)로 바꿔 같은 질문으로 비교. **완료(채택 안 함)**: EXAONE-1.2B·Qwen3-4B(4비트)·kanana-2-3b(4비트)를 질문 12개로 비교. Qwen3-4B가 규칙을 가장 잘 지켰고 kanana는 붕괴. 대체 여부는 12개로 정할 수 없음 (`decisions.md` 4-10) | 정답률·출처 표기·"모른다" 처리를 Claude와 같은 표로 비교, 응답 속도·VRAM 기록 |

**설계 원칙**
- 사실 데이터의 **정답은 추출 결과가 아니라 원문에서** 확인한다. 같은 버그가 정답과 답에 동시에 들어가면 채점이 순환한다.
- 연도 표기 주의: 음력·양력, 기원전, "~경", 연호.
- 답변 모델은 4-6에서 같은 질문으로 비교해 정한다 (Claude Opus / Sonnet / Haiku). 추출·문맥 보강 같은 대량 작업은
  가벼운 모델로 충분한지 따로 잰다. 모델 ID와 API 사용법은 구현 시점의 공식 문서로 확인한다.
- 캐싱은 접두사 일치 방식이다. 시스템 프롬프트에 날짜·난수 같은 바뀌는 값을 넣지 않는다.
- 4-10은 "서버 접속 없이 끝까지 도는 에이전트"가 가능한지 보는 실험이다. 검색(Phase 2~3)은 이미 로컬이므로 생성만 바꾼다. 모델은 구현 시점에 8GB VRAM에 들어가는 것 중 고른다(`decisions.md`에 근거와 함께 기록).

**완료 기준**: 사실 질문은 정형 조회로, 서술 질문은 RAG로 출처 달린 답이 나온다.

## Phase 5. 에이전트

**목표**: 질문을 보고 스스로 도구를 골라 여러 번 호출하고, 결과를 종합해 답하는 에이전트.

**배울 개념**: tool use(함수 호출), 에이전트 루프, 도구 설계(이름·설명·입력 스키마), 질문 라우팅,
질의 재작성, 답변 평가(LLM 심사), 관측성(trace)

| 단계 | 할 일 | 확인 |
|---|---|---|
| 5-1 | 도구 정의. **완료(도구 하나)**: `search_encyclopedia(query)`만 만듦. `era` 필터는 뺐고, `lookup_person`·`list_events`는 4-A 데이터가 필요해 5-3에서 막힐 때 다시 판단 (`decisions.md` 5-0, 5-1) | 스키마 검토 |
| 5-2 | 에이전트 루프. **완료(질문 1개 확인)**: 직접 구현(`run_agent`), 최대 5회, 도구 실패는 `is_error`로 돌려줌. 왕건 질문에서 도구 2개를 동시에 불렀고 답변 문장은 모두 근거와 일치. 다른 질문은 아직 안 봄 (`decisions.md` 5-2) | 질문 1개의 호출 과정을 로그로 확인 |
| 5-3 | 복합 질문. **완료(질문 5개)**: 광종 재위 연표·원효와 의상 비교·항목 없는 주제·구어체·두 단계 질문. 도구를 2회 이상 호출했고 항목 없는 주제는 지어내지 않았으나, 항목마다 다른 이름을 합치는 등의 오류가 보여 답변 규칙 3개를 더함(효과 입증 안 됨). 4-A를 다시 판단할 근거는 안 나옴 (`decisions.md` 5-3) | 도구를 2회 이상 호출 |
| 5-4 | 질의 재작성. **완료(질문 17개)**: 채점용 질문 17개(`src/phase5/eval_rewrite.json`)로 원문·단독 재작성·에이전트를 비교. 1위 11/12/16개, 에이전트는 17개 모두 정답 항목을 가져옴. 천장 효과·질문 수 한계가 커서 확정 아님. 재작성 단계는 따로 두지 않고 에이전트에 맡김 (`decisions.md` 5-4) | Phase 3 실패 질문 재측정 |
| 5-5 | 답변 평가셋 30개 + 채점 (사실 정확도, 출처 일치, 지어냄 여부). **조건부 완료**: 질문 30개를 단일 호출·에이전트·에이전트(규칙 없음)로 돌려 근거와 대조했고 **답변 방식을 에이전트(규칙 포함)로 확정**. 점수표(`data/score_table.csv`)는 사람의 검토 없이 초안으로 두고 더 하지 않기로 함, 규칙 3개의 효과와 재작성만의 효과는 가려내지 못함 (`decisions.md` 5-5) | 점수표 |
| 5-6 | 관측성: 질문별 도구 호출·토큰·지연 기록 (예: Langfuse). **보류**: 시스템이 복잡해지면 Langfuse를 적용하기로 하고 지금은 `run_agent`의 `log`와 `data/*.jsonl`로 둠 (`decisions.md` 5-6) | (보류) trace 화면 |
| 5-7 | (선택) 간단한 웹 UI + 배포. 앱 이미지를 직접 쓴 Dockerfile로 빌드하고, `infra/compose.yaml`에 Qdrant와 함께 띄움 | `docker compose up`으로 UI 접속 |

**설계 원칙**
- 도구 설명은 모델이 읽는 문서다. 언제 쓰는지, 무엇을 돌려주는지 구체적으로 쓴다.
- 도구 결과에도 출처(`eid`, URL)를 포함해 최종 답변까지 출처가 이어지게 한다.
- 루프에 최대 반복 횟수를 둔다. 실패한 도구 호출은 에러로 돌려주고 모델이 다시 판단하게 한다.
- 에이전트가 단일 호출보다 정말 나은지 Phase 4의 답변과 같은 평가셋으로 비교한다.

**완료 기준**: 평가셋에서 Phase 4 단일 호출보다 정확도가 높고, 모든 답변에 출처가 있다.
