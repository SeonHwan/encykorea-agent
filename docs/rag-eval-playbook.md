# RAG 평가·개선 플레이북 (encykorea-agent에서 쓴 기법 정리)

이 문서는 한국사 백과사전 RAG 학습 프로젝트(`encykorea-agent`)에서 검색 품질과 답변 품질을 잴 때 실제로 쓴 기법을 정리한 것이다.
다른 RAG 서버에 적용할 만한 것이 있는지, 답변을 개선할 여지가 있는지 **검토**하기 위한 자료이며, 이 문서의 수치는 그 프로젝트의 것이라 다른 서버에 그대로 옮겨지지 않는다.

각 기법에는 상태를 붙였다.
- **[효과 확인]** 원 프로젝트에서 측정으로 효과를 봤다.
- **[원 프로젝트에선 개선 없음]** 원 프로젝트의 데이터·질문·조건에서 시험했으나 개선이 보이지 않아 채택하지 않았다. **다른 서버에서도 효과가 없다는 뜻이 아니다.** 아래 각 항목에 결과가 달라질 수 있는 조건을 적었다.
- **[도구]** 결과를 만드는 방법이 아니라 측정을 믿을 수 있게 하는 장치다.
- **[미확인]** 시도했으나 결론을 내지 못했거나 시도하지 않았다.

**이 문서를 쓰는 방식**: [효과 확인]이든 [개선 없음]이든 [미확인]이든 모두 **이 서버에서 직접 시험할 후보**다. 원 프로젝트의 결과로 후보에서 빼지 않는다.

## 1. 평가 설계

### 1-1. 평가 질문을 유형으로 나눠 만든다 [도구]
- 유형: 서술형(개념 설명), 사실형(연도·인물 하나), 별칭형(항목명이 아닌 별칭으로 질문), 시대형(시대·분야 조건 포함).
- 유형별로 약점이 다르게 드러난다. 사실형은 질문에 항목명이 있으면 거의 1위였고, 서술형·별칭형·시대형에서 순위가 갈렸다.
- 질문의 절반은 **본문과 다른 말로 풀어 쓴다.** 본문 첫 문장을 거의 그대로 옮긴 질문은 쉬워서 점수가 높게 나온다 (원 프로젝트에서도 이런 질문이 많아 절대 수치가 높게 나왔을 가능성을 기록했다).
- **정답 항목이 컬렉션에 실제로 있는 주제로만** 질문을 만든다. 항목이 없는 주제로 검색 품질을 재면 검색이 아니라 데이터 범위를 재게 된다. 질문마다 정답 항목이 있는지, 같은 이름의 다른 항목(동음이의)이 있는지 먼저 조회했다.
- 별칭형은 별칭이 **본문에 없고 접두사에만 있는** 질문(접두사 효과를 가장 깨끗하게 잼)과 본문 곳곳에 있는 질문(대조군)을 섞는다.

### 1-2. 두 층 라벨: 항목 라벨 + 섹션 라벨 [효과 확인]
- 항목 라벨: 정답 항목 id. 검색 결과에 그 항목의 청크가 하나라도 있으면 맞다.
- 섹션 라벨: 정답 항목 안에서 **답이 실제로 든 섹션**(`kind` + 소제목 경로). 청크의 `kind`·`path`가 같아야 맞다.
- 이유: 항목 라벨만 쓰면 섹션이 많은 항목(27개 섹션)에서 엉뚱한 섹션이 올라와도 정답으로 센다. 두 숫자의 차이가 "항목은 찾았는데 답이 든 청크는 놓쳤다"를 드러낸다.
- 같은 섹션이 청크 여러 개로 쪼개졌으면 모두 정답으로 센다.
- 정답이 여러 섹션이면 **하나라도 나오면 정답**으로 센다. 필요한 조각을 모두 가져왔는지(커버리지)는 재지 않았다. 이건 알려진 약점이다 (아래 5절).

### 1-3. 라벨은 읽고 정한다 — 소제목만 보고 정하면 틀린다 [효과 확인]
- 라벨을 소제목과 키워드로만 정했다가 3-5에서 열어 보니 틀린 곳이 있었다: 질문의 두 요점(부담 경감, 대체 세금)이 `의의와 평가` 섹션에 있었는데 소제목만 보고 제외했었다. 읽고 정정하니 섹션 기준 지표가 올랐다.
- 라벨 정정은 하나씩 고치지 않고 **모아서 한 번에 반영**하고, 정정 전·후 값을 나란히 기록했다. 기준선이 여러 번 바뀌면 이전 기록과 비교가 어긋난다.
- 라벨마다 "문장을 읽고 정함"/"소제목·키워드만으로 정함"을 구분해 기록했다.

### 1-4. 동음이의·중복 항목의 정답 처리 규칙을 미리 정한다 [도구]
- 같은 이름의 항목이 둘이면(예: 묘호 일반 설명 vs 특정 왕) 어느 쪽이 정답인지, 위로 올라오면 실패로 세는지 규칙을 먼저 적는다.
- 별칭이 두 항목에 걸려 있으면 정답을 하나로 못 정하므로 그 질문은 제외하거나 정답 2개로 명시한다.

## 2. 검색 지표

### 2-1. 지표 정의 [도구]
질문마다 **첫 정답이 나온 순위**(1부터, 결과 안에 없으면 `None`)를 구해 모은다. 모든 지표가 이 순위에서 나온다.

| 지표 | 정의 |
|---|---|
| recall@k (k=1,5,10,50) | 첫 정답 순위가 k 이하인 질문의 비율. `None`은 틀린 것 |
| MRR | 질문마다 `1/순위`의 평균. `None`은 0 |

- 검색은 **상위 50개를 한 번만** 받아 두고 recall@1/5/10은 앞에서 잘라 쓴다.
- 항목 기준과 섹션 기준을 **따로** 낸다. 질문별 순위 표(질문 id, 유형, 항목 순위/섹션 순위)를 항상 함께 낸다. 평균만 보면 질문 한두 개가 결과를 좌우하는 걸 못 본다.
- recall@50이 낮으면 정렬이 아니라 **후보 수집 단계의 실패**라서 리랭커로 못 고친다. @1은 낮은데 @50이 높으면 정렬 문제다. 이 구분이 원인 분류에 쓰였다.

### 2-2. 질문별 승패를 센다 [효과 확인]
평균 차이가 질문 한두 개 때문인지 보려고 방식 A와 B를 질문 단위로 비교해 "더 위 / 더 아래 / 같음" 개수를 센다 (hybrid vs dense: 10개 위, 2개 아래, 18개 같음). 이 비율이 한쪽으로 기울면 우연일 가능성이 낮아지지만, 개수가 작아 확률적 유의성은 말할 수 없다.

### 2-3. 측정 결과를 재현 가능하게 만든다 [도구, 중요]
- **같은 코드를 3번 돌려 질문별 순위 전체가 같은지 확인**한 뒤에만 기준선으로 기록했다.
- Qdrant 서버의 RRF는 점수가 같은 청크의 순서가 실행마다 달라져 순위가 흔들렸다 (같은 질문의 정답 순위가 31↔32로 바뀜). RRF는 순위만 쓰므로 동점이 잦다.
- 그래서 RRF를 서버에 맡기지 않고 **직접 합쳤다.** 동점은 `chunk_id` 오름차순으로 고정했다. 서버 점수와 직접 구현의 점수는 최대 2.6e-09 차이로 같았다.
- 서버 RRF 점수는 `1/(k + 순위)`에서 **순위를 0부터** 센다 (1위가 `1/60`). 1부터 센다고 가정하면 점수가 어긋난다.
- 코드를 옮기거나 파라미터를 추가한 뒤에는 **기존 측정이 그대로 재현되는지** 요약표와 질문별 순위 전체를 값 단위로 대조했다.

```python
def rrf_fuse(hit_lists, k=60):
    scores, payloads = {}, {}
    for hits in hit_lists:
        for rank in range(len(hits)):                     # rank는 0부터 (서버와 동일)
            cid = hits[rank].payload["chunk_id"]
            if cid not in scores:
                scores[cid], payloads[cid] = 0.0, hits[rank].payload
            scores[cid] += 1 / (k + rank)
    order = sorted(scores, key=lambda c: (-scores[c], c))  # 점수 내림차순, 동점은 chunk_id
    return [(payloads[c], scores[c]) for c in order]
```

## 3. 검색 개선 실험과 결과

모든 실험은 같은 질문 30개, 같은 판정으로 했다. 수치는 항목 기준 / 섹션 기준.

| 방식 | recall@1 | recall@5 | MRR | 상태 |
|---|---|---|---|---|
| dense | 0.567 / 0.533 | 0.800 / 0.733 | 0.655 / 0.620 | 기준선 |
| sparse | 0.600 / 0.533 | 0.833 / 0.833 | 0.695 / 0.645 | |
| **hybrid (RRF)** | **0.633 / 0.567** | **0.900 / 0.867** | **0.749 / 0.691** | [효과 확인] 채택 |
| hybrid → colbert 재정렬 | 0.567 / 0.533 | 0.833 / 0.800 | 0.681 / 0.643 | [원 프로젝트에선 개선 없음] |
| 문맥 주입 (LLM이 쓴 한 문장 접두) | 아래 | 아래 | 아래 | [원 프로젝트에선 개선 없음, 한계 큼] |

### 3-1. dense + sparse 하이브리드 [효과 확인]
- dense는 질문이 본문과 다른 말로 풀어 쓰였을 때, sparse는 낱말이 본문에 그대로 있을 때 강했다. 두 방식이 맞히는 질문이 달랐고, 합치면 대체로 둘 중 나은 쪽과 같거나 위였다 (26/30).
- 한쪽이 매우 잘 맞히고 다른 쪽이 못 맞히는 질문(4개)에서는 합쳤을 때 오히려 둘 중 나은 쪽보다 아래로 내려갔다. 일반 설명 글이 양쪽 목록에 걸쳐 올라와 정답을 민 경우다.
- 점수 척도(코사인 / sparse 내적)가 달라 점수를 더하지 않고 **순위만** 쓰는 RRF를 썼다.

### 3-2. colbert(토큰 단위 MaxSim) 리랭커 [원 프로젝트에선 개선 없음]
- hybrid 상위 50개를 bge-m3 colbert 점수로 다시 정렬했다. 개선 1(섹션 기준 3)·악화 6. 별칭형이 함께 내려갔다. 원인은 확인하지 못했다.
- 짧은 시험 문장에서 질문 토큰 대부분이 후보의 같은 토큰(마침표 추정)과 가장 높게 맞았고, 관련 없는 문장이 관련 있는 문장보다 점수가 높게 나왔다. 계산이 라이브러리 함수와 같아서 오류가 아니라 모델 출력이다. **이 현상이 성능 하락의 원인인지는 확인하지 않았다.**
- 후보가 컬렉션에 colbert 벡터가 없어 질문마다 후보 50개를 다시 인코딩해야 했다 (50개 약 0.9초).
- LLM/크로스 인코더 리랭킹은 시도하지 않았다 [미확인]. 이 서버에서 먼저 시험해 볼 후보다.
- **결과가 달라질 수 있는 조건 (가설)**: 이 서버의 검색이 한 방식(dense만 등)이라 정렬 여지가 크면 재정렬 이득이 날 수 있다. 질문이 짧은 키워드형이 아니라 긴 문장형이면 토큰 단위 매칭이 다르게 작동할 수 있다. 원 프로젝트는 이미 hybrid로 정렬이 좋은 상태에서 얹었고 질문이 30개였다.
- colbert 대신 크로스 인코더(질문-청크 쌍을 모델에 넣는 방식)나 LLM 점수화는 같은 후보 50개에 적용해 볼 수 있다.

### 3-3. Contextual Retrieval (LLM이 청크 맥락 한 문장을 써서 접두) [원 프로젝트에선 개선 없음, 한계 큼]
- 청크마다 항목 전체 글과 청크를 LLM에 보여 80자 이내 한 문장을 쓰게 하고 임베딩 텍스트 맨 앞에 붙였다.
- 비용 때문에 전체가 아니라 청크 2,733개(정답 항목 27개 + 무작위 500개 항목)로 문맥 없음/있음 컬렉션 두 개를 만들어 비교했다. 항목 기준 hybrid recall@1 0.933 → 0.900, MRR 0.961 → 0.942.
- **한계**: 후보 풀이 작아 문맥 없음도 recall@5가 1.000에 가까운 천장 상태였다. "효과 없음"과 "측정이 포화됨"을 구분하지 못한다. 전체 풀에서는 재지 않았다.
- 이 데이터에는 이미 `항목명 > 소제목` 접두사가 있어서 문맥 주입이 새로 더하는 정보가 적었을 가능성이 있다 (가설). **접두사가 없는 청크, 청크가 문서에서 떨어져 나와 어떤 문서인지 알기 어려운 데이터(예: 대명사가 많은 본문, 표·목록 조각)에서는 결과가 다를 수 있다.** 이 서버에서는 우선순위가 높은 후보일 수 있다.
- 시험하지 않은 변형: 문맥 문장 위치(맨 앞 말고 맨 뒤), 길이, 지시문, 모델. 한 가지 변형만 시험했다.
- q03을 열어 보니 정답 청크 점수가 모두 내려갔다. 문맥 문장이 "○○ 항목의 △△ 부분으로 …를 다룬다" 꼴로 같은 항목의 청크마다 비슷해져 청크끼리 닮았을 가능성이 있다 (가설, 청크 간 유사도는 재지 않았다).

### 3-4. 시도하지 않았거나 결론 못 낸 것 [미확인]
- hybrid 후보 수(50개씩)와 RRF 상수 k(60) 조정. 후보를 100개로 늘리면 50개에 못 들어오던 질문이 후보에 들어오는 것은 확인했으나 순위는 재지 않았다.
- 청크 크기·분할 기준 변경, 요약 청크 제거, 각주 포함.
- 질문 재작성(항목명이 없는 질문을 백과사전 표현으로). 원 프로젝트의 주된 실패 원인(4-1)을 직접 겨냥하는 후보다.

## 4. 실패 분석 (숫자 다음 단계)

### 4-1. 낮은 순위 질문을 열어 원인을 분류한다 [효과 확인]
순위가 낮거나 항목/섹션 기준이 벌어진 질문 8개를 열어, **세 방식(dense/sparse/hybrid)의 상위 6개와 정답 항목 청크의 순위**를 나란히 보고 원인을 셋 중 하나로 분류했다.

| 분류 | 의미 | 나온 사례 |
|---|---|---|
| 어휘 차이 | 질문이 본문과 다른 말로 쓰여 매칭 실패, 또는 질문에 항목명이 없어 상위 주제 항목이 먼저 올라옴 | 대부분 (신석기 그릇 질문, 이름 없이 속성만 묻는 인물 질문 등) |
| 청킹/긴 항목 | 긴 항목에서 낱말이 맞는 주변 섹션이 정답 섹션보다 위 | 1건 (확정 못 함) |
| 라벨 | 정답 라벨이 좁았거나 모호 | 2건 (1건 정정, 1건은 규칙상 유지) |

- 청킹이 **단독** 원인인 질문은 없었다. 가장 흔한 원인은 질문이 항목명을 쓰지 않은 경우였다 → 검색 방식 교체보다 **질문 재작성 단계**의 몫으로 본다 (가설, 재작성을 해 보지는 않았다).
- 이름 없이 속성만으로 사람을 묻는 질문("~한 학자이자 문장가는 누구인가")이 특히 약했다.
- 열지 않은 질문의 원인은 모른다. 분포는 연 질문의 것이다.

### 4-2. 한 항목이 상위를 독점하는 현상
별칭형에서 정답 항목의 청크가 hybrid 상위 5개를 다 차지했다. 정답이 그 항목뿐이면 문제없으나, 여러 항목이 필요한 질문에서는 약점일 수 있다 (미해결).

## 5. 답변(생성) 평가

### 5-1. 같은 입력으로 모델을 비교한다 [도구]
- 근거 글(번호 붙인 청크 5개)과 시스템 프롬프트를 **두 모델에 똑같이** 준다. 규칙을 모델별로 따로 만들면 비교가 어긋난다.
- 근거 글은 본문 정리(항목 링크 `[용어](E…)`는 용어만 남김, 각주 표시·HTML 태그 제거)를 임베딩 텍스트와 같은 규칙으로 한다.
- 근거를 질문마다 한 번 저장해 두면(답변·근거 글·토큰·소요 시간 포함) 나중에 모델만 바꿔 같은 근거로 재비교할 수 있다.
- 비교 질문은 유형별 소수로 시작했다 (8개). 읽을 답변 수가 평가의 병목이다.

### 5-2. 답변 규칙(시스템 프롬프트) 요지
1. 근거 안의 내용만 쓰고, 근거로 답할 수 없으면 "제공된 근거로는 답할 수 없습니다"라고 말한다.
2. 문장 끝에 근거 번호 `[n]`을 붙인다.
3. 항목 코드·링크는 쓰지 않는다. 4. 존댓말로 간결하게.

### 5-3. 관찰된 모델 행동 차이 (8개 질문, 일부만 원문 대조)
- 한 모델은 길고 근거가 부족하면 한계를 먼저 밝혔다. 다른 모델은 짧고 단정적이었고 근거가 부족한 것을 말하지 않았다.
- 정답 섹션이 검색 상위 5개에 없으면 두 모델 모두 질문의 핵심(예: 성립 경위)에 답하지 못했다 → 이 경우는 생성이 아니라 **검색 문제**다.
- 검색이 정답을 3위에 둬도, 또는 다른 항목의 문장에 이름만 언급돼 있어도 모델이 답을 찾아내기도 했다.
- 사실형 질문에서도 한 모델은 묻지 않은 설명을 덧붙였다 ("간결하게"만 지시해서 생긴 차이일 수 있다).

### 5-4. "모른다" 처리 평가 [효과 확인]
근거가 없거나 약한 질문 5개로 시험했다.
- (a) 데이터에 항목이 없는 주제, (b) 한국사 범위 밖, (c) 항목은 있으나 질문이 묻는 세부가 본문에 없는 경우를 섞었다.
- **호출 전에 데이터를 다시 조회**했다. 항목이 없다고 가정한 두 주제는 본문 곳곳에 근거가 흩어져 있었고, 결과는 "답했는가"가 아니라 **"답이 근거 글에 실제로 있는가"**로 판단해야 했다.
- 결과: 근거에 없을 때 두 모델 모두 사전 지식으로 지어내지 않고 모른다고 했다. 근거가 흩어져 있을 때는 모아서 답했고, 답의 세부는 근거 원문에 있었다.
- **못 잡는 것**: 서로 다른 근거 조각을 이은 문장이 근거에 그대로 있는지 사전 지식인지 구분되지 않았다 (예: 도시 일반 서술의 "전쟁으로 불탔다"와 건물 항목을 이어 특정 건물이 불탔다고 쓴 경우). 인용 번호가 맞아도 이런 문장은 못 걸러낸다.
- 검색이 정확한 항목명의 항목을 상위 5개에 못 가져온 경우도 있었다 (글자 하나 차이의 비슷한 이름의 다른 항목이 올라옴). 모델이 그 사실을 구분해 답했지만 검색 약점이다.

### 5-5. 출처 표기를 코드로 붙인다 [효과 확인]
- 출처 줄을 모델이 쓰게 하지 않고, 모델이 쓴 `[n]`을 코드가 읽어 항목명으로 바꿔 붙인다. 형식이 항상 같고 모델이 항목명을 틀리게 쓸 일이 없다.
- 같은 항목이 여러 번호로 나오면 한 번만 쓴다. 번호는 최종 답에서 지운다 (사용자에게 의미 없음). **번호를 지우기 전에 먼저 읽는다.**
- 모델이 번호를 문장 앞 끝, 마침표 뒤, 줄 끝 등 어디에 둬도 읽도록 위치를 보지 않고 `[숫자]`만 찾는다.
- 모델이 "답할 수 없다"고 결론낸 답(첫 문장 판정)에는 출처 줄을 붙이지 않는다. 안 그러면 모델이 "없다"는 답에도 번호를 붙여 무관한 항목이 출처로 나온다.
- **한계**: 출처는 모델이 쓴 번호를 그대로 믿는다. 번호가 맞는지 자동으로 재지 못했다. 출처 줄은 보증이 아니라 모델이 인용한 항목의 목록이다 (출처에 무관해 보이는 지역 항목이 나온 적이 있다).

## 6. 함정과 교훈 (다른 서버에서 같은 실수를 피하려면)

1. **자동 점검 도구를 만들면 도구 자체를 먼저 의심한다.** 답변의 낱말이 인용한 근거에 있는지를 세는 점검을 만들었더니, 번호가 문장 앞뒤 어디에 오는지를 못 읽고 한국어 어미 때문에 오탐이 많아 쓸 수 없었다. 이 점검의 숫자는 어디에도 근거로 쓰지 않았다. **사람이 의심 문장을 근거 원문에서 직접 찾아 대조**하는 쪽이 더 믿을 만했다.
2. **비용 추정은 시험 호출의 `usage`로 보정한다.** 다른 토크나이저의 토큰 수로 추정했다가 실제가 1.7배였다. 호출 수와 추정 비용을 먼저 계산해 승인받고, 상한을 두고, 결과를 한 줄씩 파일에 저장해 끊겨도 이어 받게 했다.
3. **thinking이 켜진 모델에서 `max_tokens`가 작으면 텍스트가 빈 응답이 나올 수 있다.** 생각에 토큰을 다 써서 오류 없이 빈 문자열이 온다 (2,733건 중 9건). `stop_reason`이 `max_tokens`이거나 내용이 비었는지 반드시 센다.
4. **실험 범위를 줄이면 후보 풀이 작아져 점수가 포화된다.** 비용을 아끼려고 컬렉션을 줄이면 절대 수치를 원래 측정과 비교할 수 없고, 개선 여지가 작게 측정된다. 같은 줄인 풀에서 조건끼리만 비교한다.
5. **캐시는 앞부분이 글자 하나까지 같아야 적용되고 최소 길이가 있다.** 짧은 시스템 프롬프트(약 240토큰)에 캐시 표시를 붙여도 오류 없이 무시된다. `cache_read_input_tokens`로만 확인할 수 있다. 질문마다 근거가 다른 단일 호출 구조에서는 이득이 없었다.
6. **기록은 확인한 것과 못 한 것을 구분한다.** 평균만 말하지 않고 질문별 변화, 한계, "원인은 확인하지 않음"을 같이 적었다. 틀린 설명(예: RRF 순위 시작 값)은 발견하는 즉시 정정해 기록했다.
7. **기본 경로 전환 전후에 평가 출력을 값 단위로 대조한다.** 코드 이동·인자 추가 뒤에도 같은 숫자가 나와야 한다.

## 7. 검토 요청 (받는 Claude에게)

아래를 **이 문서를 읽는 쪽의 RAG 서버**에 대해 검토하고 답해 주세요. 먼저 서버의 청킹, 임베딩, 검색, 생성 구성을 파악하고, 원 프로젝트와 다른 점을 적은 뒤 진행해 주세요.

1. **적용 가능성**: 1~5절의 기법 각각에 대해 이 서버에 적용 가능한지와 이유. **[원 프로젝트에선 개선 없음]인 기법을 후보에서 빼지 말 것.** 이 서버에서 제외하려면 이 서버의 구성(데이터, 이미 쓰는 기법, 질문 유형) 때문에 시험할 필요가 없다는 근거를 대고, 근거가 없으면 시험 후보로 남긴다. 원 프로젝트에서 달랐을 수 있는 조건(3절의 가설)이 이 서버에 해당하는지 확인해 주세요.
2. **평가셋**: 현재 평가 질문이 있는지. 없다면 유형 설계(1-1), 두 층 라벨(1-2), 라벨 검증(1-3)을 이 서버의 데이터에 맞게 어떻게 만들지. 질문은 정답 문서가 컬렉션에 실제로 있는 주제로 고른다.
3. **측정 가능성**: 기준선(recall@k, MRR, 질문별 순위)을 낼 수 있는지, 결과가 재현되는지(2-3). 동점 처리나 비결정적 요소가 있는지 확인.
4. **개선 여지**: 이 서버의 검색(후보 수, 하이브리드 여부, 재정렬)과 생성(프롬프트 규칙, "모른다" 처리, 출처 표기) 중 개선 여지가 큰 곳. **추정과 확인을 구분**해 주세요. 직접 측정하지 않은 것은 가설로 표시해 주세요.
5. **함정 점검**: 6절의 함정 중 이 서버에서 이미 발생했을 가능성이 있는 것 (빈 응답, 인용 번호 검증, 비용 추정 오차 등).
6. **시험 계획**: 모든 후보([효과 확인] 포함, [개선 없음]·[미확인] 포함)를 시험하려고 한다. 비용이 작은 순서, 이전 시험에 의존하는 순서(예: 기준선 → 하이브리드 → 재정렬)를 고려해 **시험 순서와 단계별 비용**을 제안해 주세요. 각 시험은 "무엇을, 어떤 지표로, 대략 얼마의 비용으로, 어떤 결과면 다음으로 넘어가는지"를 적을 것. 한 번에 한 가지만 바꿔 효과를 가를 수 있게 설계해 주세요.

주의:
- 수치를 그대로 옮겨 기대하지 말 것. 원 프로젝트는 질문 30개, 사람이 골랐고, 일부 라벨은 읽지 않고 정했다. 효과가 있었던 것이 이 서버에서도 있다고, 없었던 것이 없다고 가정하지 말고 모두 이 서버의 평가셋으로 확인할 것.
- 외부 호출(비용)이 드는 실험은 호출 수와 추정 비용을 먼저 제시하고 사용자 확인을 받은 뒤 진행할 것.
- 사용자의 서버·데이터를 바꾸는 작업은 제안만 하고, 실행은 사용자가 승인했을 때만 할 것.
